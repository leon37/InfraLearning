# 一、引擎层

## 1.1 推理引擎是什么

**模型只是一堆权重数字，一个几十 GB 的文件，它自己什么都不做。** 必须有程序把它加载进显存、按模型结构做矩阵运算、把结果转成 token。**推理引擎就是那个程序。**

类比：`.mp4` 自己不会播放，要播放器；模型权重自己不会推理，要引擎。**引擎和模型不是前后关系，是程序和它读的数据的关系。**

用 PyTorch 写十几行 `model.generate()` 也是推理引擎，只是最原始的那种——一次一个请求、KV cache 预分配、没有批处理优化，**GPU 利用率极低**。所以 vLLM 这类东西解决的不是"能不能跑"，是**"能跑多快、多省卡"**。

### 请求的完整路径

```
用户 HTTP 请求（通常是 OpenAI 兼容接口）
   ↓
引擎的 HTTP 服务层        ← 收下、排队
   ↓
引擎内部的调度器          ← 决定这一轮把哪几个请求凑成一批
   ↓
前向计算：用显存里的权重算出下一个 token
   ↓
（循环：新 token 追加进去，接着算，直到结束）
   ↓
流式返回
```

### 两层调度（这个对比面试里很好用）

| | K8s 调度器（我写的） | 引擎内部调度器 |
|---|---|---|
| 决定什么 | Pod 落在哪台机器、哪张卡 | 这一毫秒哪几个请求凑一批 |
| 时间尺度 | 秒~分钟 | 毫秒 |
| 资源单位 | 节点、GPU 卡 | 显存块、批次里的位置 |

**我的调度器把 Pod 放到卡上就不管了；引擎的调度器在那张卡上每毫秒都在做决策。两层互不干涉，但上层决策的质量（给了哪张卡、跟谁挤在一起）直接决定下层能榨出多少吞吐。**

## 1.2 KV Cache

**大模型一个字一个字往外蹦，每写一个新字都要回看前面所有的字。**

"回看一个字"不便宜——要对它做一堆计算才知道它在这句话里是什么意思。而**第 1 个字的计算结果，在写第 2 到第 500 个字时全都要用**。每次重算，写到第 500 个字时第 1 个字已经被重复理解了 499 次。

**所以把算过的存下来，这就是 KV Cache。**

**为什么能缓存**：注意力机制里，当前 token 产出 Query，前面每个 token 各产出 Key 和 Value。**Key 和 Value 只取决于那个 token 自己和它前面的内容，后面新生成的字不会改变它们**，所以算一次就永久有效。Query 是当前 token 的，每次新算，缓存不了。

（对比：BERT 那种双向模型，后面来个新字会把前面所有字的表示改掉，就没法缓存——**只有单向生成模型能这么干**。）

### 关键数字（70 亿参数模型）

| | 占用 |
|---|---|
| 模型权重 | 约 14 GB，加载后不变 |
| 单个请求的 KV Cache | 每 token 约 0.5 MB，2000 token 的对话约 **1 GB** |
| 同时服务 50 个这样的请求 | 约 **50 GB** |

**缓存比模型本身大三倍多，而且这 50 GB 是运行时才产生的。**

### 跟我的项目什么关系（这条最重要）

**训练的显存占用启动那一刻就定死了**（参数 + 梯度 + 优化器状态，算得出来）。
**推理的显存占用取决于此刻有多少人在说话、每人说了多长——运行时才知道，而且随时在变。**

> **所以推理服务的显存需求根本没办法写死在 Pod 的 `resources.requests` 里。这就是推理的资源调度比训练难的根本原因。**

## 1.3 PagedAttention

**要解决的问题**：KV Cache 会一直长，但事先不知道会长多长。

传统做法是**按最坏情况预留一块连续显存**（比如能装 2048 token）。两个浪费同时发生：

1. **划了 2048、实际只用 300**，剩下的空着谁也用不了。而大部分请求都短。
2. **必须连续**。请求来来走走，显存被切得七零八落全是小空洞，**总量够但拼不出一块连续的**，新请求进不来。

结果：**显存利用率常年只有百分之二三十。**

**解法：把操作系统的虚拟内存分页搬到显存里。**

- 显存切成**固定大小的小块**（比如每块装 16 个 token 的 KV）
- **要多少领多少，用完再领**，不预留
- **物理上不需要连续**，靠一张块表记住"这个请求的第几段在哪一块"

**不预留 → 没有内部浪费；不要求连续 → 没有碎片。利用率提到 90% 以上。这就是 vLLM 的核心。**

白送的好处：多个请求前缀相同时（同一个 system prompt）可以**共享同一批块**，谁要改再复制——**就是写时复制，跟容器镜像那个 COW 是同一招。**

### 跟我的项目什么关系

**显存从"要么够要么不够"变成了一个可以精细计量的池子。** 因为块是固定大小按需分配的，**引擎随时知道"我还剩多少块、还能再接几个请求"**——这个数字可以暴露给上层，**扩缩容和调度决策才有了真实依据，而不是拍脑袋按最大值预留。**

> JD 里"实现细粒度显存、算力资源调度"，**前提就是引擎层先把显存管成了可计量的块。**

## 1.4 continuous batching

GPU 一次算一个请求太浪费，要凑批。**但传统凑批有个大问题：**

```
凑齐 8 个请求一起算
   请求 A 生成 20 个字就完了
   请求 B 要生成 500 个字
→ A 算完也得干等，整批必须等 B 结束才能返回、才能收下一批
```

**短请求被长请求拖死，GPU 大部分时间空转。**

**continuous batching：谁生成完了就立刻放走，空出的位置马上让新请求补进来。** 批次动态流动，GPU 一直满载。

**它和 PagedAttention 是配套的**——正因为显存按块管理，才能随时踢掉一个请求、塞进一个新的。

## 1.5 三个引擎的区别

| | 出身 | 定位 | 代价 |
|---|---|---|---|
| **vLLM** | UC Berkeley，开源 | **事实标准**。PagedAttention + continuous batching，通用、快、生态最好、支持的模型和硬件最广 | 基本没明显短板 |
| **TGI** | HuggingFace | 跟 HF 生态绑得紧，开箱即用 | 性能和活跃度被 vLLM 反超 |
| **TensorRT-LLM** | NVIDIA | **性能天花板**。把模型**提前编译**成针对特定 GPU 优化的引擎 | **只能跑 N 卡**；编译慢；换模型/卡型号/并行度都要重编 |

### 跟我的项目什么关系

前两个对调度器是黑盒，**但 TensorRT-LLM 不是**：它是提前编译的，**编译产物和 GPU 型号绑死**——给 A100 编的引擎放到 H100 上跑不了，更别说昇腾。

> **所以在异构集群里，用 TensorRT-LLM 的推理副本只能落在编译时对应型号的卡上。这是一条硬亲和性约束，是"引擎选型直接影响调度策略"的具体例子。**

# 二、服务层

## 2.1 Deployment（之前没用过，补的）

**K8s 里跑常驻服务的标准对象。** 告诉它"用这个镜像跑 3 个一模一样的 Pod"，它保证**始终有 3 个在跑**。

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  replicas: 3
  selector:
    matchLabels: {app: my-api}
  template:
    metadata:
      labels: {app: my-api}
    spec:
      containers:
      - name: server
        image: my-api:v1
```

三件事：**维持副本数**（死一个补一个）、**滚动更新**（改镜像，一个个换，不中断）、**回滚**。

### 内部是两层

```
Deployment  →  ReplicaSet  →  Pod × 3
（管版本）      （管数量）
```

**滚动更新的实现**：新建一个新版本的 ReplicaSet，把新的 replicas 一点点调上去、老的调下去。**老 ReplicaSet 不删只缩到 0，所以回滚极简单。**

### 跟我的项目什么关系

```
TrainJob    → 会结束的作业，N 个 worker 有 rank 身份、必须凑齐
Deployment  → 不结束的服务，N 个副本无身份、互相独立
```

**Deployment 里的 Pod 互相等价、可随意替换——这就是"副本"的定义。** 也正因如此 **Deployment 跑不了训练**（worker 需要不同的 RANK），这就是当初必须自己写 TrainJob CRD 的原因。

**而且我今天设计的混部对象撞上了同一个分层：**

```
Deployment         → ReplicaSet   → Pod     （K8s 原生）
InferenceJobGroup  → InferenceJob → Pod     （我推出来的）
```

都是"上层管数量和版本，下层管一组具体的 Pod"。

## 2.2 副本的三种形态（这条区分很重要）

1. **单卡副本**：1 Pod、1 张卡。小模型，最常见。
2. **单机多卡副本**：**1 Pod、多张卡**。模型单卡装不下但一台机器够，张量并行发生在这个 Pod 内部。**仍然是一个 Pod。**
3. **多机多卡副本**：模型一台机器都装不下，**必须跨机器，一个副本 = 多个 Pod**。

**前两种 Deployment 完全够用。第三种不行**——Deployment 的 replicas 是一堆互相独立的 Pod，**没有"一组 Pod 合起来算一个副本"这个概念**，scale 到 9 时它只会多起 1 个 Pod，而不是多起一组 4 个。

**这正是 LeaderWorkerSet（`kubernetes-sigs/lws`）存在的理由**：把"replicas × 每组 size"两个维度显式做进对象里，一组 Pod 一起调度、一起伸缩。**社区在推的方向是让 KServe 这类服务层用 LWS 替代 Deployment。**

**而这就是我今天推出来的那个结构。**

## 2.3 KServe

**把"部署一个模型"声明化的那一层。** 核心 CRD 是 InferenceService。

```yaml
kind: InferenceService
metadata:
  name: qwen-chat
spec:
  predictor:
    minReplicas: 2
    maxReplicas: 10
    model:
      modelFormat: {name: huggingface}
      storageUri: s3://models/qwen-7b
      resources:
        limits: {nvidia.com/gpu: "1"}
```

它的 controller 看到这个对象，自动生成：

```
InferenceService
   ├── Deployment    （vLLM 镜像 + 一个下载模型的 initContainer）
   ├── Service
   ├── HPA           （min 2 / max 10）
   └── 路由规则
```

**跟我写 TrainJob controller 是一模一样的模式：一个高层 CRD，一个 controller，展开成一堆底层对象。** 只是它的负载是推理，我的是训练。

### 比手写多做的三件事

1. **模型加载**：只写一个 `storageUri`，自动塞 initContainer 去对象存储拉几十 G 权重
2. **挑引擎**：另有 ServingRuntime 对象定义"什么格式的模型用什么镜像跑"
3. **灰度**：加一行 `canaryTrafficPercent: 10`，新版本吃 10% 流量。**手写的话得起两个 Deployment 再自己摆弄流量权重**

### 两种模式

- **Serverless**（底层 Knative）：没请求时能**缩到 0 副本**
- **RawDeployment**：普通 Deployment + HPA，不缩到零

**大模型一律用 RawDeployment**——几十 G 权重加载进显存要好几分钟，缩到零意味着下个用户等几分钟，省的那点钱不值。

### 跟我的项目什么关系

```
KServe / InferenceJobGroup   决定「要 8 个副本」
        ↓
副本层（LWS group / InferenceJob）   8 副本 × 每个 4 Pod = 32 个 Pod
        每个副本内部要 gang，凑齐 4 个才能起
        ↓
我的 scheduler   决定这 32 个 Pod 落在哪些节点、哪些卡
        每 4 个一组要在同一个 NVLink domain
        资源不够时抢占低优训练作业
```

**上下游，不是竞争。KServe 管服务化，我管资源落位。**

# 三、调度层

## 3.1 NUMA

**一台服务器上通常有两颗甚至更多物理 CPU，每颗都有自己直连的内存条。**

- CPU 0 读自己那批内存：快
- CPU 0 读 CPU 1 那批内存：**要经过两颗 CPU 之间的总线转一道** → 延迟约 1.5~2 倍，带宽也低

**NUMA = 访问内存的速度不统一，取决于访问的是哪一块。**

**一个 NUMA node = 一颗 CPU + 它直连的内存 + 挂在它 PCIe 通道下的设备**（GPU、网卡都算）。

**单位是"一颗 CPU"（一个插槽），不是"一个核"。** 消费级单路机器（比如 8 核的 9700X + 两条内存）是 UMA，所有核访问所有内存速度一样，**没有 NUMA 问题**。

NUMA 出现的两种情况：**多路服务器**（插两颗以上 CPU），或**单颗 CPU 内部由多块芯粒拼成**（AMD EPYC 可以在 BIOS 里划成多个 NUMA node）。

验证命令：
```bash
lscpu | grep -i numa
numactl --hardware
ls /sys/devices/system/node/
```

## 3.2 数据通路：为什么拓扑不止一个维度

### CPU ↔ GPU：必经主机内存

**GPU 通过 PCIe 挂在某颗 CPU 上**，所以每张卡物理上"归属"某个 NUMA node。

CPU **可以**直接寻址显存（PCIe BAR 映射），**但那条路慢到不能用来搬数据**：每次访问都是一个 PCIe 事务（几百纳秒 vs 本地内存几十纳秒），而且这段地址对 CPU 不可缓存。**只用来读写几个字节的控制信息。**

**真正搬数据走 DMA**：GPU 的拷贝引擎成批把数据从主机内存搬进显存，一次几 MB 把 PCIe 带宽吃满。**而 DMA 的源必须是主机内存，还得是"锁定"的内存**（DMA 引擎认物理地址，OS 不能中途把它换出去）。

> PyTorch DataLoader 的 `pin_memory=True` 就是把数据放进这种锁定内存。不开的话，CUDA 驱动得先偷偷拷到内部的锁定缓冲区再 DMA——多一次拷贝。

所以路径是：**主机内存（锁定）→ DMA 走 PCIe → 显存**。要不要多绕一趟 CPU 间总线，**取决于这块内存和这张卡是不是在同一个 NUMA node 下**。

### GPU ↔ GPU：可以不经过内存

```
有 NVLink：  GPU0 ←→ NVLink ←→ GPU1        直接卡对卡
没 NVLink：  GPU0 → PCIe → 主机内存 → PCIe → GPU1
```

**多卡训练的 all_reduce、多卡推理的张量并行，走的全是这条路。** 有 NVLink 是直连，没有就绕主机内存一大圈，慢好几倍；两张卡还跨了 CPU 的话再多绕一趟。

### 所以拓扑是三个维度

| 谁和谁通信 | 走哪条路 | 受什么影响 |
|---|---|---|
| CPU ↔ GPU | 必经主机内存，走 PCIe | **NUMA 亲和性** |
| GPU ↔ GPU | NVLink 直连（或绕内存） | **NVLink / PCIe 拓扑** |
| 网卡 ↔ GPU | GPUDirect 可直达显存 | **两个都要** |

### 典型 8 卡训练服务器

```
NUMA node 0：CPU0 + 内存A + GPU 0,1,2,3
NUMA node 1：CPU1 + 内存B + GPU 4,5,6,7
        两个 node 之间靠 UPI / Infinity Fabric 连着
```

**调度器说"这台机器有 4 张空闲卡"——但如果那 4 张是 2、3、6、7 呢？** 3 和 6 跨了 CPU，张量并行的通信直接掉带宽。

> **"给你哪 4 张卡"直接决定训练吞吐，而现有机制里没有任何一层能在调度决策时看见它。**

## 3.3 Topology Manager

**在 kubelet 上。** 它解决的是"分配的第二步"。

```
第一步（调度器）：Pod 去哪个节点          ← 只看总量够不够
第二步（kubelet）：在这个节点上，具体给哪几个核、哪块内存、哪张卡
```

**调度器从来不做第二步。** CPU Manager 分核、Memory Manager 分内存、Device Manager 分设备——**没有 Topology Manager 时它们各分各的、互不通气**，可能 CPU 挑在 NUMA 0、GPU 挑在 NUMA 1。

Topology Manager 作为协调者，先问每个 Manager "你能提供哪些拓扑选项"，找一个大家都能满足的共同 NUMA node，再让各自照此分配。

### 四档策略

| 策略 | 行为 |
|---|---|
| `none` | 不协调，各分各的（默认） |
| `best-effort` | 尽量对齐，对不上也让 Pod 跑 |
| `restricted` | 对不上就拒绝 Pod，**但"跨 node 本来就是最优解"的情况算对得上** |
| `single-numa-node` | **必须全部落在同一个 NUMA node**，做不到就拒绝 |

严格程度递增。**前两档是"优化"，后两档是"保证"，而保证的代价是拒绝 Pod。**

区别的例子（机器 2 个 node、每个 8 核）：
- 要 12 核 + 1 GPU：单 node 装不下必须跨 → `single-numa-node` **拒绝**，`restricted` **接受**
- 要 4 核 + 1 GPU（卡在 node 1，但 node 1 只剩 2 核）：只能 CPU 在 node 0、GPU 在 node 1 → `best-effort` **接受**，另两档都**拒绝**

### 三个硬限制

1. **只有 NUMA 一个维度。** Device Plugin 上报的 `TopologyInfo` 只有 NUMA node ID，**NVLink / NVSwitch domain 根本没地方放**——而那才是多卡场景真正关心的。
2. **调度器完全不知情。** 它跑在 kubelet 上，是 Pod **已经被调度过来之后**才起作用的。于是：

```
调度器：这节点有 4 张空闲卡，够 → 调度过去
kubelet：这 4 张分散在不同 NUMA，满足不了 → 拒绝（TopologyAffinityError）
Pod：回到 Pending
调度器：（不知道原因）这节点有 4 张空闲卡，够 → 又调过去
```
**死循环。根子是"决策的人看不见约束，看得见约束的人没有决策权"。**

3. **策略是节点级的**（kubelet 启动参数），不是 Pod 级的。没法说"这个训练作业必须严格同 NUMA，那个推理服务无所谓"。

## 3.4 DRA（动态资源分配）

**一句话：把设备从"一个计数"变成"一组能描述属性的对象"，并让调度器在选节点时就用上这些属性。**

老办法给调度器的全部信息就是 `nvidia.com/gpu: 8`——**8 张卡在调度器眼里完全一样。**

**转变的类比：hostPath → PVC/PV。** 以前挂存储只能写个路径，后来能说"我要 10G、要 ReadWriteMany、要这个 StorageClass"。**DRA 对设备做的是同一件事。**

| DRA 对象 | 对应存储 | 作用 |
|---|---|---|
| **ResourceSlice** | PV | 节点上报：我这儿有哪些设备、各自什么属性 |
| **DeviceClass** | StorageClass | 设备类别和通用选择规则 |
| **ResourceClaim** | PVC | 申领：我要几个设备、满足什么条件 |

ResourceSlice 里的属性是结构化键值对：

```
device: gpu-2
  memory:       80Gi
  model:        H100
  numaNode:     0
  nvlinkDomain: "0"      ← 老机制里没地方放的正是这行
```

### 关键：调度器真的参与了

```
调度器在 Filter 阶段读各节点的 ResourceSlice
  → 拿 ResourceClaim 里的条件去匹配
  → 匹配得上，这节点才算可行
  → 选定后把「具体分配了哪几个设备」写回 ResourceClaim 的 status
  → kubelet 照结果准备设备
```

**那个"调度器扔过去、kubelet 拒绝、又扔回同一台机器"的死循环，从根上消失了。**

### 最要紧的能力：跨设备约束

ResourceClaim 里能写**跨设备约束**——要求申领到的这几个设备某个属性必须**相同**：

> 给我 4 个设备，要求它们的 `nvlinkDomain` 是同一个值。

**这一句就是"我要 4 张互相 NVLink 直连的卡"，也正是老机制表达不了的那个需求。**

另外它天然支持**共享**：多个 Pod 可以引用同一个 ResourceClaim 共用设备——对推理场景直接有用。

### 版本

alpha 起于 1.26，中间重新设计过一次（引入"结构化参数"），之后进 beta 并逐步 GA。**面试里别硬报版本号**，说"这两年从 alpha 一路推到 GA，是社区在设备调度上的主线演进方向"就够。

# 四、面试用的三句话

**① 把自己的位置说清楚（最有用的一句）**

> 我的能力在**调度侧**——CRD、Operator、scheduler 扩展、gang、配额、抢占，这些是我自己逐行写的。**推理引擎侧我是空白**，vLLM、KServe 没有实操过。但我清楚这两块的接口在哪：**推理引擎决定单副本要多少显存、能扛多少并发，调度器决定这些副本落在哪张卡、跟训练怎么混部。**

**② 为什么推理的调度比训练难**

> 训练的显存启动那一刻就定死了；**推理的显存取决于此刻有多少人在说话、每人说多长，运行时才知道且随时在变——所以写不死在 requests 里。** PagedAttention 把显存管成可计量的块之后，引擎才知道自己还能接几个请求，细粒度显存调度才有了依据。

**③ 关于拓扑（诚实版，不要说"我撞到过"）**

> 我在设计的时候意识到，**我的 Filter 只有"够不够"这一个维度，没有"连得好不好"**。而多卡张量并行时这几张卡的互联方式直接决定吞吐。后来搞清楚这个限制的根子在 Device Plugin——**它给调度器的只是一个计数，设备属性和拓扑没地方放**；kubelet 的 Topology Manager 能补一点，但只管 NUMA、只在节点内、而且是调度之后才起作用，对不齐只能拒绝 Pod。**社区的答案是 DRA。**

# 五、诚实边界

以下**全部没有实操过**，被追问一律直说，然后给出理解停在哪一层：

- vLLM / TGI / TensorRT-LLM：没部署过，没调过参
- KServe / 模型网关 / 灰度发布：没用过
- MIG / 显存隔离 / 时间切片 / vGPU：概念清楚，没配置过
- 昇腾 / 异构算力：没接触过硬件
- DRA：没写过 driver，没在集群里开过
- 大规模集群排障：只有 kind 两节点
- 真实 GPU：**整个项目跑在 kind + CPU + Gloo 上，没有真 GPU / NCCL / RDMA**

**最后一条是最致命的边界，也是最容易补的**——租一台云上的 GPU 实例跑半天，成本一两百块，就能把"只在 CPU 上模拟过"改写成"在真实 GPU 上用 NCCL 验证过"。**优先级排在补更多概念之前。**
