## 贯穿全场的一个毛病（先看这条）

2026-08-11 一晚犯了三次：**做的选择是对的，但讲成了没有理由的选择。**

- 配额放控制器 → 说成"当初没做取舍"
- victim 选谁 → 说成"选优先级最低的"
- Permit 超时 60s → 说成"凭经验和实验"

**面试官扣的从来不是那个值，是"你不知道什么在支配这个值"。** 凡被问到"这个参数/这个位置为什么这么定"，先答**它受谁约束**，再说你选了多少。

还有一个口头习惯，同晚犯三次：**把 CRD 说成会做事的东西**（"CRD 完成了配额准入"、"触发另一个对象的 Reconcile"）。CRD 只是数据载体；**controller 之间唯一的通信媒介是 apiserver 上的对象**，没有函数调用、没有消息通道。讲清这条反而是加分项，因为它引出你架构里最干净的一条线：**scheduler 只碰 PodGroup，controller 只碰 TrainJob 的 phase，谁也不越界。**

## Q1 配额准入为什么放在控制器层？

**坐标系先甩**：我这是 **Kueue 式**（控制器/工作负载层准入，调度之前）；对面是 **Volcano 式**（配额在调度器内，跟着调度周期算）。

**买到**：① 分层干净；② 调度器保持简单，只管 gang 和抢占；③ **配额不够的作业卡在 Queued，连 Pod 都不创建**，不往调度器堆永远调度不上的 Pending Pod。

**代价**（关键在讲法）：两层异步，**准入 ≠ 物理装得下**。但这句要接成——

> **而这恰恰是我必须在调度器侧做抢占的原因。** 上层逻辑账和下层物理账会各说各话，抢占就是兜住这个不一致的机制。

锚点：跑过 job-high 被准入却塞不下、走 PostFilter 抢掉 job-mid。

另两条代价顺口带：配额只看总量、看不到节点级装箱，可能准入了却因碎片放不下；我是**单档硬顶**，无跨队列公平/借用/reclaim（Volcano 三档 guarantee/deserved/capability，Kueue nominalQuota + cohort 借还）。

## Q2 排队策略有什么问题？会不会饿死作业？

我的规则：按优先级排序，**取优先级最高、且配额放得下的**。

**这个"且"是陷阱。** 余量 4 核，队头是 8 核高优作业进不去，第二个是 2 核低优作业进得去 → 跳过高优放低优 → 小作业不断流入，**余量永远攒不到 8 核**。

**被饿死的是高优先级的大作业，凶手是源源不断的低优小作业**——方向和直觉相反。（"低优被高优插队"不是缺陷，那是优先级的设计意图。）

**标准解**：资源预留（reservation）+ 受限回填（backfill）——队头作业攒不够时把资源记账预留给它，后来的小作业只能用预留之外的部分，或只在**不推迟队头启动时间**的前提下回填（HPC 的 EASY / conservative backfilling；Volcano 有 reserve 和 backfill 两个 action）。

**归纳这一句最值钱**：

> 「预留」在我这套系统里是同一个母题在两层各缺了一次——控制器层没给队头大作业预留配额，调度器层没给抢占腾出的资源预留（NominatedNodeName）。**两个缺口是同一个病：系统里没有"资源预留"这个概念，所以哪一层都挡不住插队者。**

## Q3 只做了 CPU，搬到 GPU/NPU 怎么办？

**先记住：NPU = 国产 AI 加速卡**（主要指华为昇腾 Ascend），接入方式跟 GPU 一样，资源名换成 `huawei.com/Ascend910`。JD 里 GPU/NPU 并列 = 有信创/国产化需求。

**绝不能说"逻辑差不多"**——这是送命答案，在面试官最想听差异的地方说了没差异。

**接入路径（这块我答对）**：走 **kubelet 的 Device Plugin**（DaemonSet 向 kubelet 注册 → kubelet 把 `nvidia.com/gpu: 8` 写进 node 的 capacity/allocatable → 调度器从 NodeInfo 看到）。**调度器侧就是一个 extended resource，Filter 逻辑基本不用改。**

**四条真差异（每条都让我的项目更必要，不是更没用）**：

1. **整数、不可压缩、不可超卖。** CPU 是时间片资源（cgroup 的 quota/period，500m = 每 100ms 给 50ms），超卖了只是变慢，属于**可压缩资源**；GPU 要不到就是跑不了。**碎片化杀伤力不是一个量级**——8 卡机散着 8 个单卡任务，8 卡训练永远进不来 → 直接放大 Q2 的大作业饥饿，**预留从优化项变成必需品**。
2. **gang 在 GPU 上才是刚需。** CPU 场景凑不齐是浪费可超卖的时间片，损失软；GPU 场景占住的卡是独占的，空转期间全集群一点都用不了。
3. **抢占代价从"重启进程"变成"烧机时"** → 见 Q4。
4. **我确实缺的三样**：多维公平（DRF）、拓扑感知、显存共享（MIG / 时间片 / MPS）。

**这句是全场最值钱的一句**（把做过的接到没做过的）：

> 我在 DDPLab 里用 Gloo 跑过多 worker 的 all_reduce、观察过通信在单步耗时里的占比，所以我理解为什么 GPU 调度不能只看"这台机器还剩几张卡"——**同样 8 张卡，全 NVLink 互联和跨 PCIe 的 all_reduce 带宽差好几倍，调度器给你哪 8 张直接决定训练吞吐。** 我的 Filter 目前只有"够不够"这一个维度，没有"连得好不好"这个维度。

**术语兜底**（能说一句话定义就够，别往深挖）：
- **DRF**：多资源下"公平"没法定义（按核分内存大户吃亏，按内存分反之）。做法是找每个队列**占集群比例最高的那种资源**当主导资源，拉平各队列的主导资源占比。性质：谎报需求不划算、无人想换、不比平分差。**对 gang 天然不友好**（逐任务分，分到一半凑不齐）。
- **MIG**：A100/H100 的**硬件切分**，最多 7 份，各有独立 SM / L2 分片 / 显存，**故障和性能都真隔离**（时间片共享做不到）。规格写作 `1g.5gb`。K8s 里 mixed 策略下资源名变成 `nvidia.com/mig-1g.5gb`，调度器还是按名字匹配。**坑：切分是节点级静态配置，改切分要重置 GPU 赶走任务** → 集群散着一堆小实例、整卡任务拼不出来，是 Q2 碎片问题的升级版。
- **拓扑感知有两层**：节点内是 kubelet 的 **Topology Manager**（协调 CPU/Memory/Device Manager 做 **NUMA 对齐**，策略 none/best-effort/restricted/single-numa-node；不对齐则 H2D 拷贝要跨 socket 走 UPI，带宽掉一截）；卡间是调度器层的 GPU 拓扑分配（NVLink/NVSwitch vs 跨 PCIe switch vs 跨 socket）。

## Q4 抢占时怎么决定杀谁？

**我的实现**：单 victim（没做多 victim 组合），从"驱逐后能让抢占方跑起来"的候选里选**优先级最低**的。

**但优先级只回答了"谁该让路"（权利问题），没回答"杀谁最不心疼"（代价问题）。** GPU 场景下这是四位数人民币的差别：两个同样低优、同样腾出 4 卡的候选，一个刚起 5 分钟、一个跑了 20 小时。

**正确的度量不是"已运行时长"，是「自上次 checkpoint 以来的时长 × 卡数」**——能续跑的作业，真正损失的只是最后一个 checkpoint 之后那段。

**闭合杀手连接问**：

> 如果作业**不能**从 checkpoint 续跑，代价就是全部已运行时长——**那么在 GPU 集群上抢占在经济上根本不成立，没有平台敢开这个开关。checkpoint 不是抢占的配套功能，是抢占的前提条件。**

**整卡语义反过来打自己的缺口**：CPU 上杀一个腾 3.5 核、要 3.2 核，几乎刚好；GPU 上杀 4 卡作业腾 4 张、要 3 张，**多的 1 张纯浪费（给不了别人半张）** → **多 victim 组合优化在 CPU 上可有可无，在 GPU 上是刚需。** 比单纯承认"我没实现多 victim"高一档。

**业界基线**：kube-scheduler 默认的 victim 选择也不只看优先级，还会**尽量少杀**（把候选逐个试着放回去看能不能不杀）、优先选违反 PodDisruptionBudget 最少的。**"最低优先级"只是排序的第一个键。**

## Q5 Permit 超时设多少？怎么定的？

**别说"凭经验"。** 正确答法：

> 这个值由两个约束共同决定，取更大的那个：① 同组 pod 依次走完调度周期的时间；② **victim 优雅终止 + 资源回收 + 重新调度的时间**。**主导的是第二个。** 我现在设 60 秒，是 kind + CPU 环境下的实验值；上 GPU、训练进程退出前要写 checkpoint 时，grace period 会放大到分钟级，这个超时必须跟着一起放大。

**深水区（这才是这题的考点）**：抢占时间线是 PostFilter 标记 victim → victim 被删但**不是瞬时的**（`terminationGracePeriodSeconds` 默认 30s，进程还要退出、kubelet 还要回收）→ 下一轮调度周期抢占方才可能 Filter 通过。

**这整段时间里抢占方在 Permit 等待室的 pod 必须活着。** 超时太短 → 等 victim 真死、资源真腾出来时，**抢占方的等待室已经被自己的超时清空了** → 抢占白做，下一轮还是同样时序，还是赶不上 → **活锁**。

所以：纯 gang 场景短超时的受害者是凑齐；**一旦有抢占，短超时的受害者是抢占本身，而且这条约束严得多**（同组 pod 走调度周期是毫秒到秒级，victim 终止是几十秒级的物理过程）。

超时太长的代价（这条我答对了）：整组确实起不来时，waitingPod 长期霸占资源。

## Q6 controller-runtime：Reconcile 什么时候会再来？

**默认不会再来。** 返回 `ctrl.Result{}, nil` 的语义是"处理完了，别再叫我"——**队列里没这个 key 了**，直到下一个事件。**没有任何定时器在后面兜着推进状态机。**

想让它再来只有三条路，**全都得自己要**：
1. **新事件**——watch 的对象变化被重新入队（主力）。
2. **`ctrl.Result{RequeueAfter: 30 * time.Second}`**——唯一的"定时"，逐次显式声明。
3. **返回 error**（旧写法 `Requeue: true`）——进限速队列，指数退避，默认 5ms 起翻倍、封顶 1000s。

**容易记混的**：informer 的 resync（manager 的 `SyncPeriod`）**默认 10 小时**还带抖动，是防状态漂移的兜底，**绝不能当状态推进的动力**。

**推论（排雷清单里"状态机自驱动"隐患的根）**：凡是"等一会儿再来看看"的逻辑必须显式 `RequeueAfter`。**自驱动只在有事件流时成立；事件断了，状态机就死在那儿——不报错、不重试、悄无声息。**

**Pod → TrainJob 的事件映射**：`Owns(&corev1.Pod{})`，底层是 informer watch 到 Pod 事件后，通过 Pod 的 **OwnerReference** 反查属主，把 TrainJob 的 NamespacedName 入队。

**QueueController 的触发源**（别只举一个例子，答这句）：**队列可用额度或候选集合发生变化的任何时刻**——作业结束释放额度、新作业提交进 Queued、Queue 配额被人工调大。

**连续放行这段（已验证代码，可以自信讲）**：

> 放行动作会更新 `queue.Status`，QueueController watch 自身，所以这一轮放行会触发下一轮继续放，直到额度用尽——status 不再变化，update 不发出去，循环自然收敛。**幂等写在这里同时挡掉了 hot loop。**

（hot loop = 自己改自己 status 又被自己 watch 到，若无条件写 status 就永远停不下来，打满 CPU、刷爆 apiserver。这是 controller 开发最常见的事故之一。）

## 边界：被问到这些，诚实划线

- **Volcano / Kueue**：没在生产用过、没通读源码。真实经历是**先自己设计实现、事后对照公开设计逐条比对**——这个说法含金量更高，也不怕追问。（别说"基于它们的处理逻辑写的"，会被听成照着抄。）Volcano 的 Session/Action 执行模型只到"知道它是批量调度"这一层。
- **DDP**：跑过、看过指标、懂启动契约，训练脚本不是我写的。**够用的三句**：数据并行、每张卡完整模型副本、切的是数据；每步 all_reduce 要全员到齐 → all-or-nothing → 需要 gang；前提是模型塞得进单卡。**被问 FSDP 分片策略 / 通信重叠 / bucket 调优就划界**：「我的定位是平台侧，训练框架我理解到能据此设计调度约束的程度，具体并行策略调优不是我做的。」对平台岗这是正确的分工，不丢分。
- **潜在追问**：TorchElastic / `torchrun --nnodes=1:4` 的弹性训练可以动态伸缩、成员变化会重新 rendezvous——这会顶我"world_size 定死"的绝对化论断。这块是空的，被问到直接承认没接触过。
- **GPU 实操**：MIG、DRF、拓扑感知都是概念清楚、没有实操。
- **验证环境**：kind + CPU + Gloo，非真实 GPU / NCCL / RDMA。
