# 训推混部设计（推理负载接入）

> 建立时间：2026-08-13
> 状态：设计推导完成，未开始实现
> 相关项目：`~/AIInfraTrainJob`、`~/AIInfraSchedulerPlugin`

---

## 1. 为什么做这件事

**外部触发**：2026-08-13 同花顺「AI 基础设施」一面，面试官在反问环节给的建议是"你这个项目是基于训练的，可以再去玩一玩基于推理的"。同一天科大讯飞约面，JD 是「云原生 AI 推理平台」，七条职责里五条是推理侧。

**市场判断**：真正训基座模型的公司是少数，做推理服务的是多数。护城河项目扎在训练侧，与主流岗位需求存在一格错配。

**为什么选混部而不是重做**：现有资产里**只有 gang 那一块是训练专有的**，CRD/Operator 开发、scheduler 扩展、配额准入、优先级、抢占全都是推理平台照样要的。而混部场景（推理高优常驻、训练低优可抢占，白天推理吃资源、晚上训练捡空闲）**恰好就是这些机制的应用场景**——不需要新建能力，只需要加一类负载。

叙事上从"我做了个训练调度器"变成"我做了个训练推理混部的算力平台"。

---

## 2. 推理与训练的本质差异

以下都是从"推理服务是常驻的、按 QPS 弹性伸缩的、副本互相独立的"这三条推出来的，不是抄来的分类。

| 维度 | 训练 | 推理 |
|---|---|---|
| 任务形态 | 有限作业，跑完结束 | 常驻服务，永不结束 |
| 关心的指标 | 吞吐、完成时间 | P99 延迟、可用性 |
| 成员性质 | worker 有唯一 rank 身份、必须互相通信 | 副本无身份、零通信、完全可互换 |
| 少一个成员 | 整体零产出 | 少一份容量 |
| gang 粒度 | 整个作业 | **单个副本内部**（仅多卡推理） |
| 部分成功 | 灾难 | **常态** |
| 资源需求 | 启动时固定 | 随 QPS 动态变化 |
| 配额语义 | 一次性准入（进门收票） | **持续计量** |
| 资源不够时 | 能等（还没开始服务） | **等不起（正在服务）** |
| 抢占代价 | 自上次 checkpoint 的机时 | 在途请求直接失败 |

**最关键的一条是最后三行**：训练可以老老实实排队，推理不能。这一条逼出了后面所有的设计差异。

### 2.1 一个重要的例外：多卡推理里 gang 会回来

小模型单卡推理，一个副本 = 一个 Pod，副本之间不需要 gang。

**但大模型单卡装不下时，一个副本要用张量并行拆到多张卡上**——这几个 Pod 之间必须通信（每层矩阵乘都要 all_reduce），少一个副本就起不来。**副本内部又是 all-or-nothing 的。**

所以：**gang 在推理场景不是失效，是粒度从"作业"降到了"副本"。** 副本之间独立，副本内部 all-or-nothing。

推论：多卡推理副本的那几张卡~~**必须走 NVLink 互联**~~（张量并行通信量极大），所以拓扑感知在推理场景同样是刚需。

> ⚠️ **2026-09-17 实测修正：这句要加前提，"必须"在小模型上不成立。**
> （原句不删，按 X → Y → Z 记。实测细节见 `~/AIInfraGPULab/docs/实验台账.md`「里程碑 4」第 9 条。）
>
> - **X（本文原判断）**：张量并行通信量极大 → 多卡副本必须 NVLink，否则会被通信拖垮
> - **Y（上机预测）**：在一台**没有 NVLink、连 P2P 都不可用**（`topo -p2p r = NS`）的双 A10 上跑
>   Qwen2.5-1.5B 的 `--tensor-parallel-size 2`，预测每步 56 次 all-reduce 的开销压过切分收益 → 会变慢
> - **Z（实测）**：**反而快 30%**。c1 Mean TPOT 8.18 → 5.70 ms，c8 输出吞吐 882 → 1240 tok/s（+41%），
>   KV 总容量 575,664 → 1,273,968 token（每卡只需装一半权重）
>
> **为什么**：decode 每次 all-reduce 只传 1 个 token 的 hidden（`1536 × 2 字节 ≈ 3 KB`），
> **瓶颈是延迟不是带宽**；而张量并行让每卡只读一半权重，decode 本来就是显存带宽 bound，这笔省下来的更值钱。
> prefill 才是 MB 级（c8 一次约 4.9 MB × 56 层 ≈ 275 MB，按 SHM 14.65 GB/s ≈ 19 ms，与实测吻合）。
>
> **所以正确的说法是**：**当每层激活达到 MB 级、通信占比压过计算时**，多卡副本才必须走高速互联；
> 1.5B 这种规模下，TP 的收益（权重分摊）大于代价。拓扑感知仍是刚需，但**门槛比原文写的高**。
> ⚠️ **"多大算大"没有拐点数据**，这台机器造不出拐点（decode 的消息量始终是 KB 级）。

## 3. 推理负载走现有链路，哪些环节会断

现有链路：

```
提交 TrainJob → Submitted → Queued
  → QueueController 算配额，够就放行
  → Starting：创建 Service / PodGroup / N 个 worker Pod
  → 自定义 scheduler：PreFilter → Filter →（不够则 PostFilter 抢占）→ Permit 等待室
  → 凑齐 minMember 整组放行 bind → Running → Succeeded
```

逐段核对：

**① 状态机 —— 断**
推理常驻，永远跑不到 Succeeded，现有状态机没有对应的终态语义。

**② 配额准入 —— 不是失效，是不够**
现有实现只在 `Queued → Starting` 那一刻算一次配额，之后不管。
推理的总需求 = 单副本资源（固定）× 副本数（动态），**每一次扩容都是一次新的准入请求**。一次性准入模型撑不住。

**③ PodGroup —— 粒度和数量都变了**
训练：一个 TrainJob 对应一个 PodGroup，建一次就不动。
推理：**一个副本对应一个 PodGroup**，数量 = replicas，**扩容要新建、缩容要删**。面对的是一个动态的 PodGroup 集合。

**④ Permit 等待室 —— 单卡副本天然不受影响**
现有插件开头就有这段判断：

```go
_, ok := pod.Labels["pod-group"]
if !ok {
    return framework.NewStatus(framework.Success)
}
```

**没有 `pod-group` 标签的 Pod 直接放行。** 所以单卡推理 Pod 只要不打这个标签，进调度器就是走完 Filter 直接 bind，等待室根本不碰它。

**这说明插件从设计之初就是"gang 负载与非 gang 负载可以共存"的**，~~混部在调度器这一层不需要改代码~~。

> ⚠️ **2026-09-14 读代码 + kind 复现修正：最后半句是错的。**
> （原句不删。复现记录见 `~/AIInfraGPULab/docs/实验台账.md`「里程碑 4」缺口 1 那节。）
>
> - **X（本文原判断）**：非 gang Pod 直接放行 → 混部在调度器这一层不用改代码
> - **Y（读代码）**：上面那段 early-return 在 **Filter / Permit** 里成立；但 **PostFilter 开头有一模一样的一段**，
>   在那里它的含义是"不选任何 victim，直接返回 `Success`"。而 PostFilter 链**遇到 `Success` 就短路**，
>   `DefaultPreemption` 又在调度器配置里被 disable 了
> - **Z（kind 复现）**：低优训练作业占满卡后，起一个高优、无 `pod-group` 的 Pod → **谁都不去抢，它一直 Pending**
>
> **正确的说法**：非 gang 负载**能被调度**不用改代码，但**要能触发抢占必须改**。
> 顺带一提，把 `DefaultPreemption` 放回来也不行——实测它会排在自定义插件前面，**连 gang 作业也一起接管**，
> 破坏原有的整组抢占。最终方案是 InferenceJob 最小切片（见 `~/AIInfraGPULab/README.md`「M4 的两条线和推进顺序」）。

多卡副本则相反：需要 PodGroup，`minMember` = 张量并行度。

**⑤ 扩容时资源不够 —— 处理方式与训练相反**
训练凑不齐 → 整组失败退回重来（起一半等于零产出）。
推理凑不齐 → **能起几个起几个**（扩到 9 个也比 8 个强），起不来的那部分排队等；有低优训练可抢就抢。
**注意排队的是"一个待创建的副本"，不是整个推理服务——服务本身一直在正常提供。**

## 4. 对象模型

### 4.1 两层切分

副本数是**服务级**属性，gang 的 minMember 是**副本级**属性，两者生命周期不同，必须拆开。

```
InferenceJobGroup (服务级, replicas=8)        TrainJob (作业级, minMember=8)
    └── InferenceJob × 8 (副本级, minMember=4)     └── PodGroup
            └── PodGroup                                 └── Pod × 8
                  └── Pod × 4
```

**InferenceJob 与 TrainJob 同级**：在调度器眼里它们是同一类东西——**一组需要 gang 调度的 Pod，对应一个 PodGroup**。

### 4.2 字段（初稿，未定型）

**InferenceJobGroup**
- Spec：`Replicas`（会被外部改）、`QueueName`、`Priority`、单副本的资源与模板
- Status：聚合计数，**必须能区分"在等资源 / 启动中 / 失败"三种情况**——只有一个 `RunningReplicas` 表达不出来，而这三种情况的处理完全不同（等资源要考虑抢占、启动中只要等、失败要告警）

**InferenceJob**
- Spec：`MinMember`（= 张量并行度）
- 对应一个 PodGroup

### 4.3 状态的分层原则

**下层持有真相，上层持有聚合。**

- InferenceJob 自己有状态：它是独立对象、有独立生命周期
- InferenceJobGroup.Status 是对下层的聚合：给外部一个概览，免得谁想知道服务健不健康都得列举所有 InferenceJob

**上层的数字必须永远可以从下层重新算出来，绝不能是唯一记录**——否则一旦对不上就无法自愈。

实现方式：InferenceJobGroupController 通过 `Owns` watch 自己的 InferenceJob，聚合后写进自己的 Status。**与 TrainJob Owns Pod、聚合出 phase 是同一套模式。**

**聚合计数每次 Reconcile 重新算，不做增量加减**——与 QueueController 算 `Used` 时选择"遍历重算"而非 `+= / -=` 是同一个原则。

### 4.4 与社区的对照

这套两层结构与 **`kubernetes-sigs/lws`（LeaderWorkerSet）**几乎一致——LWS 专为多机多卡推理设计，一个 LWS 管 `replicas` 个 group，每个 group 是 leader + N worker、整组 gang 调度，Spec 就是 replicas 和每组 size 两个维度。

**这是第二次独立撞对社区分层**（第一次是 TrainJob + PodGroup 撞上 Volcano 的 vcjob + PodGroup）。

待办：对照 LWS 的实际定义，看有哪些字段是自己没想到的。

## 5. 配额与抢占：两层账的新形态

### 5.1 配额口径必须统一

Used 的算法：单副本资源 × 副本数，与现有 QueueController 遍历重算的方式保持一致。**改动点是把遍历范围从只有 TrainJob 扩展到也包含 InferenceJobGroup。**

**但不能按 `RunningReplicas` 算。**

训练那边是**准入通过就扣额度，Pod 都还没创建**。推理若按已 Running 的副本数算，会出这种问题：期望 10 个、准入 10 个、只有 6 个 Running，**Used 只算 6 个的量 → 队列里凭空多出 4 个副本的空额 → 别的作业进来占掉 → 那 4 个等待的副本永远起不来。**

**两类负载的配额口径必须一致：都按"已准入的"算，不是"已跑起来的"。**

### 5.2 抢占要分两层，而现有实现只有一层

推理扩容失败有两种原因，走的是完全不同的路径：

| 缺什么 | 谁来发起抢占 | 现状 |
|---|---|---|
| 物理资源不够 | scheduler 的 PostFilter | ✅ 已有，一行不用改 |
| **配额不够** | **QueueController** | ❌ **完全没有** |

**为什么配额不够时 scheduler 帮不上忙**：现有架构是「配额准入通过才创建 Pod」（Kueue 式分层最得意的一点：不会先创建一堆调度不了的 Pod 堆在调度器里）。配额不够 → **Pod 根本不会被创建 → scheduler 看不到任何东西 → 连抢占的机会都没有。**

**为什么训练不需要这一层**：训练撞到配额不够，卡在 Queued 排队等就行，反正还没开始。**推理等不起——它正在对外提供服务。**

**所以控制器层抢占是推理逼出来的新能力**，也是这套设计里目前最大的缺口。

## 6. 未决问题

- **控制器层抢占怎么做**：选哪个训练作业让出配额、怎么让它优雅退出、退出后配额怎么交接给推理、失败如何回滚
- **谁改 Replicas**：接 HPA / KPA，还是自己实现按 QPS 的扩缩容
- **命名**：`InferenceJob` 带 Job，但它是常驻的，在 K8s 语境里 Job 强烈暗示"会结束的批处理"，可能误导
- **拓扑感知**：多卡推理副本的几张卡必须 NVLink 互联，现有 Filter 只有"够不够"没有"连得好不好"
- **滚动更新 / 灰度发布**：换版本时先起新副本再删旧副本，期间资源需求翻倍（surge），资源不够时怎么办
- **推理副本被抢占的优雅性**：不能像训练那样直接标记驱逐，必须先从 endpoint 摘流、等在途请求处理完再终止，需要配合 readiness probe 和 PodDisruptionBudget

## 7. 面试讲法

被问"你只做过训练，我们这儿是推理"时：

> 是的，我的项目目前是训练侧的。**但我最近正好在往训推混部的方向扩**——推理服务作为高优常驻负载、训练作业作为低优可抢占负载，共享同一个资源池。我的抢占和配额机制正好是这个场景需要的。
>
> 现在做到的是对象模型这一层：推理需要**两层对象**，服务级管副本数、副本级管 gang，因为多卡推理时**一个副本内部又是 all-or-nothing 的**——gang 在推理里不是失效，是粒度从作业降到了副本。这个分层后来发现跟社区的 LeaderWorkerSet 是同一个思路。
>
> 推导过程里撞到一个我原来架构上的真实缺口：**我的抢占只做在调度器层，但推理扩容时如果是配额不够，Pod 根本不会被创建，scheduler 连抢占的机会都没有**——所以控制器层也需要一层抢占。训练不需要它，因为训练可以排队等；**推理等不起，这是推理逼出来的。**

**最后那段是重点**：它展示的不是"我做完了"，是"我能从约束推导出架构、并且发现自己原有设计的边界"。
